00 — 开场,45 秒

我研究的不是「怎么在知识图谱上答题」

语言模型可以直接给出答案,也可以给出一段推理。但两者都不必然可执行,也不必然可审计。更麻烦的是:当结果错了,你很难判断错在「没读懂问题」还是「程序写错了」。

我的毕设问的是:能否先把问题压缩成一个结构化的语义任务表示,再展开成可执行程序,然后用确定性环境去验证、修复和筛选这些推理轨迹,最后只用验证通过的那部分训练更小的模型。

子问题一

如何让模型先理解任务,而不是直接猜一整个程序?

→ Interpreter / Planner 分离

子问题二

如何验证中间推理,而不只检查最终答案?

→ Grounding / Executor / Verifier / Reflector

子问题三

如何从模型自己生成的候选轨迹里得到可靠训练数据?

→ 验证通过轨迹训练

开场不要做的事

不要从 OCDS 字段、节点数量、166,277 份公告讲起。知识图谱是验证系统的地基,不是这次交流的主角 —— 它值 45 秒,不值 5 分钟。

01 — 语义前缀

让模型先从问题本身抽出前置信息,并预测出大致的逻辑链

这是整个设计里我最想跟你讨论的一步,因为它和你 UPFT 的直觉是同一类问题:一条自动生成的推理轨迹里,究竟哪一段是可靠、可迁移、值得学的?

为什么不能让 Planner 一次生成完整程序

如果直接要求模型一次性吐出完整 JSON 程序,它必须同时完成六件事:理解问题、匹配 schema、选实体和字段、组合算子、填参数、控制输出格式。任何一个局部错误都会让整个程序失败 —— 而且失败之后,你无法定位错误属于哪一类。

Interpreter 实际输出什么(真实样本)

问题来自训练集,briefing 是教师模型的真实输出,未经修饰:

// 问题
"...for Powys County Council, under CPV 85000000,
 which supplier is listed on the contract notice
 awarded to ABICARE SERVICES LIMITED?"

// Interpreter 输出的 briefing
answer_signature: { operation: "select", value_type: "entity",
                    answer_field_text: "supplier" }

program: [
  { id: "A", op: "filter_records", inputs: [], args: { filters: [
      { field_text: "release_year",       value: "2025" },
      { field_text: "buyer organisation", value: "Powys County Council" },
      { field_text: "CPV code",           value: "85000000" } ] } },

  { id: "B", op: "filter_records", inputs: ["A"], args: { filters: [
      { field_text: "supplier_name", value: "ABICARE SERVICES LIMITED" } ] } }
]

它承诺了什么

  • 答案签名 —— 操作、值类型、要返回的字段
  • 逻辑链的形状 —— inputs: ["A"] 明确了 B 依赖 A,中间依赖是显式的
  • 显式约束 —— 问题里出现的实体、年份、类别

它不承诺什么

字段仍然是自然语言:"buyer organisation"、"CPV code"。它们还没有绑定到 KG 的规范槽位 —— 接地发生在后面。

所以 briefing 是一棵带依赖的程序骨架,但字段还悬空。

你的 UPFT 说:一条推理轨迹的早期部分,可能比完整轨迹携带更多可迁移的信号。我的 Interpreter 走的是同一个直觉,但前缀不是前 k 个表面 token,而是一个语义前缀 —— 答案签名、显式约束,加上一棵依赖有序、字段仍是自然语言的程序骨架。

所以它引出的问题是:可靠的前缀,能不能由语义边界来定义,而不是由固定 token 长度?

3,855条已验证轨迹带完整 briefing(共 5,598 条)
403条含真实中间依赖(inputs 非空)
9个意图模板 + bridge_join + unanswerable

他一定会追问,而你必须先承认

「不拆分时准确率是多少?你做过 Interpreter 的消融吗?」

没有做完整消融。不要说「已经证明拆分有效」。正确的说法是:

拆分给了我一条可控的错误边界 —— 语义理解和可执行规划之间有了分界,失败时我能判断是哪一级出的问题。Interpreter 的系统性消融正是我还想补上的那块。

02 — 接口

这一层其实和后端无关 —— 底下换成什么都行

回头看刚才那份 briefing,注意一件事:它里面没有任何一样东西是知识图谱专有的。 字段是自然语言("buyer organisation"、"CPV code"),算子是通用的集合操作。 它描述的是「这个问题需要什么」,而不是「到我的 KG 里该怎么取」。

所以 Interpreter 这一层,可以路由到任何能回答「按这些约束筛出记录、再聚合」的后端。 而这件事我不是在畅想 —— 我已经跑过两次了。

证据一 · 同一份计划,驱动检索后端

plan_guided_rag_baseline.py 把黄金计划里每个约束的 field 和 value 拼进 TF-IDF 查询, 取 top-40 交给阅读模型。机制完全跑通,计划确实驱动了一个纯检索后端。

结果:单记录题 21.9%,聚合题 3.3%。 所以它告诉我的不是「接口不成立」,而是哪种后端适合哪种问题。

证据二 · 同一门语言,换掉数据后端

迁移到 WikiTableQuestions 时,类型化执行架构原样保留,只把采购数据适配层换成 表格视图、列感知值链接器,再加一个保留行的极值算子。

十七个算子一个没动。官方测试 51.80%。

所以后面可以嫁接什么

  • 纯检索 / 向量库 —— 单记录、文本型问题,消融显示这里它本来就很能打
  • SQL / 数据仓库 —— 已经结构化好的表,接地那一层换成列映射即可
  • 联网搜索 / 外部 API —— KG 里根本没有的信息。注意 Interpreter 已经有一个 MISSING_OR_UNSUPPORTED_INFORMATION 字段在标记这类情况,那就是天然的路由钩子
  • 多后端混合 —— briefing 里每个 step 可以走不同后端,因为依赖关系本来就是显式的

我的访问消融其实可以当成一张现成的路由策略表来读:聚合题必须走确定性执行器(85.7% 对检索的 3.7%),单记录题检索就够用(66.5%)。

关键在于,这个判断不需要等模型自己觉得该检索了 —— 从 briefing 的结构就能读出这一步要不要穷举。

这也是和 SmartRAG 最接近的地方

SmartRAG 研究的是多个模块如何经环境反馈联合优化,以及何时该去检索。 我的 briefing 提供了一个显式的、结构化的路由依据 —— 判断依据不是模型的直觉, 而是这一步需不需要穷举。这个信号是从问题结构里读出来的,在执行之前就有。

必须说清楚的边界

我现在是单后端,没有实现路由器。plan_guided_rag 是作为对照组跑的, 不是作为产品路径跑的。所以这是一条有两个数据点支撑的设计方向,不是一个已经建成的系统 —— 这样讲才站得住。

03 — 计划语言的演进

从算子白名单,到自由组合的递归代数

这是我论文里叙事上最关键的一次转折,而且它是被实验结果逼出来的,不是设计时想好的。

诊断 — 第 7 章的组合试点

我做了一个组合泛化的小规模试点,想看学生模型能否处理没见过的算子组合。结果是:执行器支持新的桥接组合,却拒绝了两个非桥接的聚合组合。

关键结论:边界在流水线,不在学习器。限制模型的不是它学不会,而是我的计划语言写不出来。

重建 — 第 9 章的递归代数

把「算子模式的封闭白名单」换成十七种节点类型的递归代数,算子之间自由组合。谓词加入否定、析取,以及针对已计算子树的集合成员判断 —— 即半连接的推广,并配了一个反连接的孪生算子。

深度和规模设上限,树由递归类型检查器验证,失败返回带路径的类型诊断。

文法是封闭的 —— 每个节点类型和枚举都固定;但树的空间是组合开放的。这就是整个设计点:封闭枚举带来的可验证性活了下来,因为验证从「这个算子在不在白名单上」变成了「这棵树在文法下是否良类型」,而后者一样机械。

七种值类型

records 记录子集 · values 标量去重集 · groups 分组键到数值 · ranking 有序键值对 · number · value · bool

十七个节点类型

filter values count size sum exists select extreme groupby argext top num combine vcompare setop gcombine keys_where

迁移到 WikiTableQuestions 时只新增第十八个:保留行的 extreme_rows。

04 — 确定性的那一半

模型提出推理结构,但无权判定它是否正确

语言模型Interpreter

答案签名、显式约束、带依赖的程序骨架、不可答标记。不接触数据。

语言模型Planner

把骨架展开成十七算子的可执行树,在文法编译出的 JSON schema 约束下解码。

确定性Grounding

字段文本与实体文本绑定到规范槽位:候选生成、类型闸门、置信阈值、前二名差距。

确定性编译

十二个规范化变换,随后三道闸门:全程序可接地、DAG 合法、无未受约束的绑定源。

确定性执行

按依赖层级求值,精确十进制、合约级去重、可加性防护、日期感知比较。

确定性验证

分层:语法 → 类型 → 可接地 → 中间约束 → 最终答案 → 双 oracle 一致。

确定性Reflector

收到定位化失败信号,判断该改理解、算子、绑定、方向还是参数。上限三轮。

确定性拒绝

三轮后仍失败的轨迹被丢弃,不进训练集。拒答与有意义的空结果是终局。

Grounding 处理的是真实世界的脏

  • 同一机构对应多个平台账号识别码 —— 国防部单年出现 77 个
  • 名称与地址存在变体,204,711 个别名收敛成 131,502 个机构
  • 金额来源不同,award / contract / tender / lot 语义不同,直接相加就是同一笔钱算两次

所以 Grounding 不是字符串匹配,而是把模型的计划接到真实数据语义上。

Reflector 不是「让模型再想一次」

它收到的不是「答案错了」,而是定位化的执行反馈:某字段不存在、实体无法接地、算子类型不匹配、聚合导致重复计数、中间结果为空、关系方向可能相反。

边界:它能改程序,不能改执行器;不能为了拿到正确答案绕过类型和语义检查;三轮后失败的轨迹直接拒绝。

我的反思是扎根在可执行反馈上的。模型不是被要求「再想一想答案」,而是收到来自接地、编译和执行的定位化失败信号。它可以重写程序,但永远不能重写执行器,也不能为了拿到更好看的答案绕过一次类型检查。

双 oracle:为什么这个数字比它看起来重要

第二个求值器是纯 pandas 实现,与系统不共用任何执行代码,从原始节点和边表重新计算每个标准答案。

第一轮一致率只有 92.7%。关键在于不一致按题型成簇出现而非随机散落,所以可诊断 —— 揪出三个真实缺陷:桥接类隐含假设了从未写进黄金数据的「展平取第一供应商」宇宙;一个空字符串供应商名匹配了所有无供应商记录,注入固定 16.1 亿英镑误差;另有 230 个约束退化。

修正后 99.88%(14,770 例中 14,752 例)。这意味着训练标签不依赖另一个 LLM 的判断。

你 MyPhoneBench 的论点是:任务完成了,不代表执行过程符合约束。我这边的同构说法是:最终答案碰巧正确,不代表模型产生了可靠的程序。

所以我把整条链都留痕 —— 原始规划输出、接地结果、中间执行状态、验证器拒绝原因、修复轨迹,以及最终通过的那支程序。

05 — 训练数据从哪来

候选是自动生成的,训练集只装验证通过的子集

四层谱系

  1. 真实世界原始数据 —— 英国公共采购 OCDS,166,277 份 release,2022–2026。字段普查、金额语义约定、机构规范化、两阶段实体消解、typed KG。
  2. 问题与可执行任务 —— 基于 KG schema 与算子组合构造 12,828 题。问题不是凭空生成:实体关系真实存在,算子组合可执行,答案可计算。
  3. 教师生成候选轨迹 —— 云端教师产出 briefing、程序、必要时的修复轨迹。此时它们只是候选。
  4. 验证与筛选 —— schema 检查、接地、编译、确定性执行、oracle 验证、双 oracle 一致性。只有全通过才进训练集。

验收漏斗(论文 ladder 表)

但第二轮评测只涨 0.4 分,不显著。所以循环报告在实测天花板,没有继续迭代。

这条我觉得对做自训练的人最有用:验收率不是能力增益的代理指标。自采集各轮的验收率一直在涨,但第二轮的评测增益只有 0.4 分,而且不显著。

措辞纪律 — 一句话说错,意思就反了

不要说:「使用部分可验证的数据训练」。这会让人以为训练集里还混着未验证数据。

要说:从自动生成的候选中筛选出验证通过的子集,只用该子集训练学生模型。一句话:候选轨迹是自动生成的,但学生模型的最终训练集只装了执行验证通过的那些。

关于 85.65 的因果纪律

不要说「验证让学生从 69.76 提升到 85.65」。除非你有「未筛选轨迹训练」对「验证轨迹训练」的直接消融 —— 你没有。

这是相关结果,不是完整因果证明。主动讲出这个边界,反而让人觉得你清楚实验的界限。

一个只用「执行验证通过」轨迹训练的 8B 学生,在 2,285 题密封测试上到 85.65%,而提出这些训练候选的云端教师是 69.76%。这说明的是:验证过的自生成监督,足以把一个更小的专用模型训过它的老师。

要分离验证本身的因果贡献,需要「未筛选 vs 已验证」的直接消融 —— 那个我没有跑,所以不能那样讲。

07 — 与主线同等重要

组合泛化:三轮迭代,和一套专门用来打自己脸的检查电池

这一章我想重点讲,因为它不是一个结果,而是一套方法论 —— 而且它每一步都在主动寻找自己的失败。

compose probe:按组合距离设计的 324 题

近 —— 分组时序 argmax(N1)、分侧过滤求和比较(N2)。这两个正是第 7 章试点失败的形状。

中 —— 计数比值(C1a)、求和差(C1b)、分组比较(C5)。

远 —— 供应商集合差(C2)、经关系除法的全称量化(C3)、跨角色并集计数(C4)。

文法之外 —— 中位数与单调趋势(P1/P2),不存在合法的树,正确行为是弃答。

交集 holdout 是全章最锋利的一格:一个训练中从未出现的构造,靠组合它已被示范的兄弟算子完美解出,而基座只做对一半。

四件我主动做来打自己脸的事

一、泄漏审计杀掉了我自己的头条

v1 原本 92.66%。审计发现导出器只在合成池内部断言了 shape 不相交,而旧任务翻译通道把 196 个简单 shape 漏回训练。重切后 B_clean 91.72%(+814/−5)—— 这才是我认的 v1 结果。

二、评估器审计与掩码负控制

用独立实现重新评分模型产出的 300 棵树:300/300 判定一致,无执行器侧偏差。把实体和年份换成占位符的掩码负控制,准确率崩到 6% —— 正如它应该的那样。

三、析因边界实验 —— 最有意思的一个

C5 失败到底因为措辞不匹配,还是没见过示范?把 probe 问题改写成训练文风:没变(1/40),表面假设否定。塞两个 worked example 进 prompt:直接 100%(32/32 与 40/40)。

失败的全部原因是示范缺席。

四、索赔纪律规则

一个构造一旦进入 recipe 库,它的 probe family 就不再算泛化证据,只算 coverage repair。泛化主张只建立在测量当时从未被示范过的格子上。

每轮退休一个 holdout、轮换一个新的进来,保证任何时刻都存在从未示范的格子。

诚实账本 — 这个你一定要主动讲

v2 修好了 C3 和 C5,却把跨角色并集 C4 从 40/40 打到 7/40。原因:v1 那 40/40 本来是白嫖基座模型的泛化,而「as a buyer or as a supplier」不出现在任何 recipe 表面,v2 更紧的拟合把这个继承来的行为挤掉了 —— 模型开始静默丢弃第二个角色。另有一个弃答控制从 6/6 滑到 4/6。

两个回退在任何头条指标上都看不见,只有常设扰动电池抓得到。

这是那条线的第二个方法论发现,也是我真正愿意为之辩护的一条:在合成数据迭代中,每一次渲染修复都会在别处收窄分布;能发现它的仪器是常设扰动电池,而绝不是头条指标。

三轮迭代:顺序敏感性的收敛

v1 每行随机打乱子句顺序 → v2 → v3 引入顺序孪生(一半训练行给同一棵树第二个子句倒序的表面)。

顺序敏感性差距:44.7 → 24.0 → 8.7 分。随机顺序把它砍半,成对孪生几乎补上。

v3 收尾:B_clean 99.17%(树合法性 100.0%),交集 holdout 仍 19/19 且仍从未被示范,probe 98.77%,旧任务保留 87.25%。

lock-in:一个关于「能力」的反直觉发现

微调把格式契约刻得太深 —— 自由解码时,它会覆盖基座发射任何其他契约的能力。但那个能力还活在底下,一旦约束解码就立刻回来。

结论:这些系统里看起来像「能力」的东西,常常是基座能力与格式通道的复合;分不开两者的仪器,会把两者都读错。

必须主动承认的限制

  • B 集由同一个 recipe 引擎生成 —— shape 未见,但渲染习语是共享的,而 reorder 结果证明习语确实有影响。
  • probe 的八个 family 是手工设计的,不是从真实用户采样。所有题面都是合成英文,这里没有任何东西测量了真实用户措辞。
  • 约 9 分的顺序扰动残差、一个弃答控制停在 4/6,冻结时仍未解决 —— 记录而不追打,避免噪声追逐。
  • 组合泛化不等于创造全新的原子算子。模型仍受限于封闭文法;真遇到缺失的原语,系统目前只能失败或请求扩展执行器。
  • 依赖引导解码这件事是被记录而非被消除的:自由解码的数字也报了,而且每个微调模型都差得多。

而这个限制正好是我最想听听你意见的研究问题:反思器能不能区分「组合错了的程序」和「真的缺一个原语」,然后主动提出一个新的可执行技能,而不是只能失败?
