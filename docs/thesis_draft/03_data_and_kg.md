# Chapter 3 — Data Engineering and Knowledge-Graph Construction

Hard verification, the organising principle of this dissertation, is only possible over a substrate whose semantics are explicit. A verifier cannot check that a sum is legitimate unless the data says which values may be summed; an oracle audit cannot re-derive an answer unless every convention the original computation relied on is written down as data rather than remembered as folklore. This chapter describes how five years of UK Open Contracting Data Standard (OCDS) releases become such a substrate: a typed, convention-explicit, audit-first knowledge graph of 215,221 contract-award nodes and 131,502 canonical organisations [ARTIFACT-VERIFIED: data/kg/nodes/contract_nodes.parquet, data/kg/nodes/org_nodes.parquet]. Two design stances carry the argument throughout. The first is *precision-first entity resolution*: a false merge corrupts every downstream count and sum, so merging is tiered, conservative, and audited, and the documented cost is under-merging rather than silent over-merging. The second is *conventions as data*: the additivity of money values, the flat first-party record universe, and the latest-release snapshot are checkable flags and stated choices, not implicit assumptions. Chapter 4's independent oracle audit and Chapter 5's verifier both lean on exactly these properties.

## 3.1 Source data and ingestion

### 3.1.1 The OCDS release corpus

The source data is the UK's public OCDS publication covering Contracts Finder and Find a Tender notices, distributed as one compressed JSON-Lines file per year for 2022–2026. Each line is a *compiled release*: a self-contained JSON snapshot of one contracting process, identified by a stable `ocid`, carrying the buyer reference, a `parties` array with the full organisation records, a `tender` block (title, CPV classification, estimated value, procurement method, lots, periods), an `awards` array (suppliers, award values, related lots), and a `contracts` array (signed values and dates). The five year-files contain 166,277 release records in total (source analysis: ocds_data_analysis.md), with a pronounced volume jump in 2025 when the Procurement Act 2023 introduced new mandatory notice types. A release is a snapshot of a *process*, not a contract: multiple releases of the same OCID can appear within and across year files as the process moves from notice to award to signature.

Ingestion (`src/procurement_graph/ingest/loader.py`) streams each gzipped file line by line — no file is ever loaded whole — parses each release defensively (malformed lines are logged and skipped, missing `ocid` or `date` rows are dropped), and flattens each release into one row with the nested `parties` and `contracts` arrays serialised as JSON strings so that the interim Parquet file has a simple, universally readable schema. Deduplication then keeps, for every OCID, the release with the latest ISO-8601 `date` (string comparison is safe because all dates are ISO-formatted), recording in a `source_years` column every year-file in which the OCID was observed.

The *latest-release snapshot* is the first of the chapter's explicit conventions, and it is a choice with alternatives. Modelling full amendment chains would preserve every correction, but multiplies schema complexity for question families the benchmark never asks; keeping the first release would discard corrections. Taking the latest release matches the publisher's own compiled presentation and yields exactly one authoritative snapshot per contracting process. The convention is stated here and stress-tested by the oracle audit of Chapter 4: the knowledge graph answers questions about the latest published state of each process within the ingested corpus, not about publication history and not about UK procurement in its entirety.

A second, wider extraction pass (`src/procurement_graph/extract/tables.py`) re-reads the raw files to capture fields the first pass does not, producing seven tables (tender core, lots, award criteria, awards, bid statistics, text evidence, documents). Alignment with the deduplicated snapshot is enforced structurally rather than by convention: a raw release is accepted only when both its `ocid` *and* its release `id` match the winning release chosen at ingestion, guaranteeing that the extracted tables are row-for-row consistent with the interim snapshot.

### 3.1.2 Quality problems the pipeline must absorb

Three families of data-quality problems, all documented at analysis time and all visible in the code paths that handle them, shaped the design.

**Money semantics.** Where a contract's value lives is inconsistent across the corpus. In the 2024 population, `awards[].value` was null in every inspected record; the reliable signed value sits in `contracts[].value.amount`, joined to its award through `awardID`; `tender.value.amount` is a pre-award *estimate* present in roughly a third of records (source analysis: ocds_data_analysis.md). Worse, the corpus mixes genuinely additive spend with framework-agreement ceilings — multi-year umbrella values reaching tens of billions of pounds — so a naive SUM over "contract values" is not total spend. The extraction layer therefore records a `value_source` per award with a fixed precedence (`award`, then `contract`, then `tender`), never overwriting provenance, and the graph derives a boolean `value_is_additive` that is true exactly when the value came from an award or signed contract and false when it is a tender estimate. In the final graph, 160,362 award rows carry contract-sourced values, 15,640 award-sourced, 19,623 tender-sourced, and 19,596 no value at all; 176,002 of 215,221 rows are flagged additive [ARTIFACT-VERIFIED: data/kg/nodes/contract_nodes.parquet]. This is the "conventions as data" stance in miniature: instead of the pipeline privately knowing that tender estimates must not be summed, the flag makes *additive-only money aggregation* a guard that the downstream executor and verifier mechanically enforce (Chapter 5), and that the build itself validates — the KG validation suite fails the build if any award- or contract-sourced value is marked non-additive or any tender fallback is marked additive (`src/procurement_graph/kg/validate.py`).

**Organisation identity noise.** The record-level `buyer` field is a bare `{id, name}` reference; the authoritative organisation records live in `parties`, and the identifiers they carry are of sharply unequal quality. Around nine in ten buyer references and 86% of supplier references use `GB-FTS` platform identifiers — per-profile account IDs on the publishing platform, not canonical entity identifiers: the Ministry of Defence appeared under 77 distinct GB-FTS IDs in a 2024 sample (source analysis: ocds_data_analysis.md). Name strings are noisy even when official identifiers exist (casing variants, ampersand versus "and", trailing whitespace, post-merger legal-name drift), and some source strings are simply malformed — organisation names with duplicated suffixes such as "… NHS Trust Trust Headquarters" appear verbatim in the data and later surface in Chapter 7's error analysis, where the correct system behaviour on such an unresolvable mention is a provenance-gated abstention rather than a guessed match [WORKLOG-SOURCED: cicada_worklog.md, 2026-07-05]. Section 3.3 describes the entity-resolution design these problems dictate.

**Structural multiplicity.** One release may hold several awards; one award may name several suppliers (`awards[].suppliers` is a list); lots relate awards to descriptions many-to-many. The pipeline never collapses these silently: awards are extracted one row per `(ocid, award_id)` with the supplier list serialised intact, and the graph gives multi-supplier awards one edge per supplier organisation (Section 3.2).

## 3.2 Graph schema and coverage

The knowledge graph (built by `src/procurement_graph/kg/`, orchestrated from `pipelines/40_build_kg.py`) is a set of typed Parquet tables — four node tables and four edge tables — whose column contracts are frozen in code (`kg/schema.py`).

| Table | Rows | Key |
|---|---|---|
| `contract_nodes` | 215,221 | `contract_node_id` = `contract:{ocid}:{award_id}` |
| `org_nodes` | 131,502 | `canonical_id` |
| `cpv_nodes` | 3,870 | `cpv_code` |
| `evidence_nodes` | 535,731 | `evidence_id` |
| `buyer_of` | 215,218 | one edge per contract node with a resolvable buyer |
| `supplier_of` | 334,063 | one edge per (supplier organisation, contract node) |
| `categorized_by` | 164,691 | contract → CPV code |
| `evidence_for` | 1,326,240 | evidence → contract, with match scope |

All row counts verified directly [ARTIFACT-VERIFIED: data/kg/nodes/\*.parquet, data/kg/edges/\*.parquet].

The unit of analysis is the *contract-award*: one node per `(ocid, award_id)` pair, spanning 118,088 distinct OCIDs [ARTIFACT-VERIFIED: data/kg/nodes/contract_nodes.parquet]. Each contract node carries the award's own fields (status, title, dates, value with `value_source` and `value_is_additive`), the release-level tender context joined in by OCID (title, CPV code and description, procurement method and category, periods), and derived conveniences computed once at build time rather than at query time: `has_award_signed_date`, `has_contract_period`, day-count intervals, and contract duration. Organisation nodes carry the canonical name and identifiers, the entity-resolution status and alias counts, region evidence aggregated across all observations of the entity, and precomputed role summaries — buyer/supplier contract counts, first and last activity years, and additive-only value sums, in which non-additive values contribute zero by construction (`kg/enrichment.py`). CPV nodes carry the code, its description, its division/group/class prefixes (making the CPV hierarchy navigable by prefix), and the same additive-only aggregates.

Coverage is reported as measured fact, not assumption: 215,218 of 215,221 contract nodes have a buyer edge; 204,186 have at least one supplier edge (334,063 supplier edges in total — 22,075 awards name more than one supplier organisation, one names 249); 164,691 carry a CPV classification; 215,202 have at least one text-evidence pointer [ARTIFACT-VERIFIED: data/kg/edges/\*.parquet]. Among organisations, 7,125 appear as buyers, 114,281 as suppliers, and 1,269 in both roles [ARTIFACT-VERIFIED: data/kg/nodes/org_nodes.parquet]. These numbers matter downstream because they fix abstention semantics: a question about the supplier of an award that has no supplier edge must produce an empty result and an abstention, not an invented supplier, and the benchmark's empty-result traps (Chapter 4) are sampled with these bounds in mind.

Why this shape? The workload is aggregate and multi-hop question answering: counts, sums, rankings, extremes, and bridge joins of the form "contracts whose supplier is also a buyer" or "top suppliers within a CPV category for a given buyer". Two properties of the schema serve exactly that workload. First, every queryable property is a *typed slot with a closed value space* — procurement category is one of goods/services/works, CPV codes come from the 3,870-row node table, organisation references resolve against the canonical table — which gives the planner of Chapter 5 concrete grounding targets and gives the verifier closed enums to check against. Second, the graph flattens deterministically into a single record universe: the query backend (`src/procurement_graph/qa/benchmark/kg_interface.py`) joins the edges into one row per contract node, carrying the full tuples of buyer and supplier canonical IDs, names, and regions, alongside scalar `buyer_name`/`supplier_name` columns defined as the first element of the sorted name tuple. This *flat first-party record universe* is the second stated convention: filters and aggregations are defined over one row per contract-award with a deterministic first-party scalar, multi-party membership remains queryable through the tuple columns and `supplier_count`, and the independent oracle of Chapter 4 recomputes answers under exactly the same stated flattening.

A deliberate non-decision completes the schema story: the graph is columnar Parquet, not a graph database. At this scale — a few hundred thousand nodes, about two million edges — vectorised dataframe joins comfortably outperform query-engine round-trips; the executor stays deterministic, dependency-free, and unit-testable; and the independent oracle audit can re-derive every answer with plain dataframes and no shared query engine. This is an argument about operational surface, not expressiveness: nothing in the workload requires traversals that columnar joins cannot express.

## 3.3 Entity resolution: conservative, tiered, audited

The alias universe contains 204,711 raw organisation identifiers, 76.9% of them notice-scoped GB-FTS platform IDs, resolving to 131,502 canonical organisations [ARTIFACT-VERIFIED: data/entities/alias_map.parquet, data/entities/canonical_orgs.parquet]. Because a single false merge silently corrupts every count and sum that touches the merged entity, resolution is organised as ordered tiers of strictly decreasing evidence strength, each recorded per entity in an `er_status` field, with everything below the evidence bar left unmerged. The realised tier sizes are: registry-identifier deterministic merges 26,704; safe deterministic variants 6,332; normalised name + region 14,875; name-only 1,286; LLM-adjudicated borderline cases 255; curated government lookup 37; and 82,013 singletons deliberately left unmerged [ARTIFACT-VERIFIED: data/entities/canonical_orgs.parquet, `er_status` value counts].

**Phase 1 — deterministic, registry-anchored** (`src/procurement_graph/er/phase1.py`). Any party observed with an official registry scheme — Companies House (GB-COH), NHS organisation codes (GB-NHS), UK Provider Reference Numbers (GB-UKPRN), the charity registers (GB-CHC, GB-SC, GB-NIC), or the Mutuals register (GB-MPR) — takes that registry identifier as its canonical ID, with a fixed priority order when several schemes are observed for one raw ID. A single, tightly scoped cross-referencing rule then attaches platform IDs to these anchors: when, *within one OCID*, a GB-FTS party and an officially identified party share the same normalised name, the GB-FTS ID becomes an alias of the official entity. The OCID scoping is the safety property — the co-occurrence of both identifiers on the same notice is direct evidence they denote one organisation, whereas the same name match across unrelated notices would not be. Crucially, GB-FTS identifiers are never themselves canonical: they are notice-scoped platform artefacts, and treating them as entity keys is precisely the fragmentation failure (one ministry, 77 nodes) the design exists to avoid.

**Phase 2 — heuristic but bounded** (`src/procurement_graph/er/phase2.py`). Entities left unresolved by Phase 1 pass through a small curated lookup of well-known government bodies (37 canonical entities, e.g. `GOV-MOD` for the Ministry of Defence, which ultimately absorbs 1,222 aliases — the largest alias group in the table [ARTIFACT-VERIFIED: data/entities/alias_map.parquet]); then exact normalised-name + region grouping, where the normaliser (`common/normalise.py`) uppercases, strips accents and punctuation, rewrites ampersands, and removes legal-form suffixes (LIMITED, LTD, PLC, LLP, CIC, …), and groups of more than one raw ID sharing a normalised name and region merge under a stable content-hashed `MERGED-*` identifier; name-only merging is the fallback for entities with no region evidence. Everything still unmatched becomes a *singleton* keeping its own raw ID as a provisional canonical ID. Fuzzy string matching was deliberately demoted: the Jaro-Winkler candidate generator (`er/candidates.py`) is a read-only analysis tool with blocking and hard output caps that produces human-review files and *never* writes to the entity tables.

**Safe-merge extension — audited, cluster-checked.** A later ablation framework (`src/procurement_graph/experiments/er_ablation.py`, applied by `scripts/apply_safe_er_merges.py`) generated candidate pairs with risk flags (scheme conflicts, parent/child and subsidiary patterns, acronym ambiguity, procurement-agent patterns), passed the deterministic-safe subset and an LLM-adjudicated borderline queue through cluster-level checks, and applied the surviving merge edges by union-find. Canonical-ID election within a merged component prefers official registry IDs (in scheme-priority order), then curated `GOV-*` IDs, then existing `MERGED-*` IDs; the LLM tier contributes only 255 of 131,502 canonical entities, every one carried with `er_status='llm_safe_merge'` so it can be inspected, discounted, or reverted wholesale. The two extension tiers account for the `deterministic_safe_merge` (6,332) and `llm_safe_merge` (255) statuses in the audit trail.

**The audit trail.** Every canonical entity — merged or singleton — has one row in `er_audit.csv` recording its canonical ID, display name, resolution status, official scheme, alias count, and the full pipe-delimited list of raw IDs it absorbs (131,502 rows [ARTIFACT-VERIFIED: data/entities/er_audit.csv]). Together with the `alias_source` column of the alias map (phase1 / phase2 / safe-merge / unresolved), every merge decision in the graph is reconstructible after the fact. The build additionally verifies referential closure: every alias target must exist as an organisation node, or the build fails.

**Residual ambiguity is handled at query time, conservatively.** The design makes no recall claim: its documented cost is that decoration variants of one organisation — "The X" versus "X", "X (BEIS)" versus "X", casing differences — can survive as distinct canonical rows, splitting one organisation's records across variants. The runtime policy (`src/procurement_graph/reasoning/entity_resolution.py`) is the single, shared gate through which every planner and repair path resolves an organisation mention, so that no caller silently takes the top hit of a weak match. Its logic, directly from the code: an exact record match or a ≥0.999 score resolves immediately; otherwise the top candidate must score at least `min_score = 0.85`, and if a second candidate also clears that bar, the top must lead by a margin of at least `min_margin = 0.10` — unless all contenders collapse to one *decoration-variant equivalence key* (casefold; strip a leading "the" and a trailing parenthetical alias; unify "&"/"and"; drop punctuation), in which case the mention is resolved but *every* variant is surfaced so the executor filters with an `IN` over all of them rather than undercounting on one. Genuine ambiguity — distinct equivalence keys within the margin — refuses to resolve, feeding the abstention path. A minimal, evidence-driven mention-expansion table (currently the single rule ICB → "Integrated Care Board", added when the audit showed the graph stores full names while questions use the abbreviation) is applied only when the literal lookup finds nothing. Both mechanisms were introduced *after* the Chapter 4 oracle audit identified variant splits and abbreviation mismatch as the ambiguity classes with practical impact — an instance of the thesis-wide discipline that conventions and repairs are adopted in response to measured failures, then written down.

## 3.4 Provenance: evidence nodes and why they exist

The fourth node type stores no structured facts at all. The 535,731 evidence nodes hold the corpus's long free-text fields — lot descriptions (332,802), tender descriptions (164,373), selection-criteria descriptions (21,429), review details, and performance terms [ARTIFACT-VERIFIED: data/kg/nodes/evidence_nodes.parquet] — extracted verbatim with their OCDS field paths, covering 166,257 distinct OCIDs, essentially the whole release corpus. They are deliberately kept out of the structured record universe: paragraphs are not queryable slots, and storing them as contract-node attributes would blur the line between what the executor can filter on and what it can only cite.

Their purpose is provenance. The `evidence_for` edge table (1,326,240 edges reaching 215,202 of 215,221 contract nodes) links each text fragment to the contract-award nodes it describes, at lot scope when the fragment's lot ID matches a specific award's related lots and at OCID scope otherwise, with the resolution recorded in a `match_scope` column (`lot`, `ocid`, or `ocid_fallback`) so that the precision of every provenance link is itself queryable. Downstream, this is what makes *provenance-gated abstention* concrete rather than rhetorical: every answer must trace to specific records, answers are returned with evidence samples attached, and when a question's constraints match no records — an unresolvable "NHS Trust Trust" mention, a year with no awards for the named buyer — the system returns an explicit empty-evidence abstention instead of a fluent guess. The benchmark's empty-result abstention family (Chapter 4) tests precisely this contract.

## 3.5 Engineering properties that matter scientifically

Several build-level decisions are reported here not as implementation trivia but because downstream scientific claims rest on them.

**Determinism.** The build is a pure function of its inputs: no randomness, stable sort orders before every deduplication, content-hashed merge identifiers, and modal-value tie-breaks resolved by deterministic ordering. Phase 2 of entity resolution is explicitly idempotent — re-running it on already-processed outputs repairs rather than duplicates canonical rows (`consolidate_duplicate_canonical_orgs`). Deterministic rebuilds are what make the Chapter 4 oracle audit meaningful (two independent implementations can only be compared over a reproducible substrate) and what make the benchmark's gold programs stable across the project's lifetime.

**Validation-gated writes.** The builder runs a validation suite — primary-key uniqueness for every node table, `(ocid, award_id)` uniqueness, referential closure for every edge endpoint, alias-target closure, value-additivity consistency, and coverage measurements — and *refuses to write* the graph if any check fails; coverage numbers are emitted as warnings into a machine-readable report (`kg/build.py`, `kg/validate.py`). The counts quoted in Section 3.2 are therefore properties the artifact is guaranteed to have, not properties it happened to have once.

**Stable composite keys.** `contract_node_id = contract:{ocid}:{award_id}` names the unit of analysis, and every edge ID embeds its endpoints (`buyer:{canonical_id}:{node_id}`), making edges self-describing and set-semantically deduplicable. When one award names several raw supplier IDs that resolve to the same canonical organisation, the build collapses them into a single edge whose `raw_id` field carries the sorted JSON list of contributing raw IDs — multiplicity is normalised away from the graph's semantics but preserved in its provenance.

**Empty strings are a first-class hazard.** Missing values throughout the corpus arrive as empty strings, not nulls, and the build treats them accordingly: supplier IDs that are empty or unresolvable produce no edge rather than an edge to an empty organisation; CPV edges are emitted only for non-empty codes; derived flags (`has_award_signed_date`, `has_contract_period`) are computed by explicit non-empty tests. The one place this hazard escaped into computation — an early bridge-family oracle in which an empty-string party name matched every record lacking that party, inflating every bridge sum by a constant — was caught by the dual-oracle agreement audit and is dissected in Chapter 4; it is the concrete illustration of why this chapter insists on conventions being checkable.

## 3.6 What the knowledge graph hands to the rest of the thesis

The chapters that follow consume the substrate built here through a deliberately small contract. The *grounding targets* are the typed slots and closed value spaces of Section 3.2: the planner must land on real fields, real CPV codes, and canonical organisations, and anything else is mechanically rejectable. The *verifier guards* are the explicit conventions: additive-only money aggregation via `value_is_additive`, the flat first-party record universe, the latest-release snapshot, and the decoration-variant `IN`-filter policy. The *abstention semantics* are fixed by the measured coverage bounds and by provenance: empty result sets are meaningful, expected outcomes with dedicated benchmark traps, not failure modes. None of this makes the graph "ground truth" — correctness downstream is always relative to the conventions this chapter documents, a relativity Chapter 8 lists among the limitations — and none of it claims complete coverage of UK procurement, only of the ingested corpus. What it does claim, and what the artifact-verified validation gates support, is that the residual ambiguity of the substrate is documented and bounded, which is the property everything downstream is built against. Chapter 4 constructs a 12,828-question benchmark by executing parameterised plans directly against this graph; Chapter 5 builds the compile–ground–execute–verify chain over the same typed interface.
