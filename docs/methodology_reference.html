A2 · 实体消解:两阶段瀑布 代码核实

实现在 src/procurement_graph/er/phase1.py 与 phase2.py。核心原则是精确度优先:上层判不了才交给下层,而模糊匹配永远不写入合并。

Phase 1(确定性)

  1. collect_parties(releases_df) —— 从 releases 抽出全部 party 观测,统计 raw_id 数与覆盖的 OCID 数。
  2. 官方编号解析 —— 按 raw_id 分组,_best_canonical_for_raw_id(grp) 从官方注册方案(scheme)里选出最佳 canonical_id。
  3. 同 OCID 内的 GB-FTS 交叉引用 —— _cross_ref_fts_aliases():同一份公告内出现的 GB-FTS 编号,可借该公告内已解析的官方编号链接过去。
  4. 输出 —— canonical_orgs_df(每个规范实体一行)与 alias_map_df(raw_id → canonical_id 的多对一映射)。 关键细节:alias_map 覆盖全部 raw_id,未解析的 GB-FTS 单例也在里面,带 er_status='unresolved' 标记 —— 也就是说没有记录被悄悄丢弃。

Phase 2(受控合并)

  • apply_gov_lookup() —— 用政府机构对照表匹配。
  • merge_by_name_region() —— 规范化名称 + 地区证据联合判断,_make_merged_id(norm_name, region) 生成合并 ID。
  • consolidate_merged_groups() / consolidate_duplicate_canonical_orgs() —— 合并组归并,_modal() 取众数、_aggregate_org_type() 聚合机构类型。
  • build_audit_log() —— 每一次合并都写审计日志。这一条在论文里很值钱:合并是可回溯的。

论文/草稿 结果:204,711 个原始别名 → 131,502 个规范机构,其中 82,013 个单例保持未合并。国防部单年出现 77 个平台身份。

写论文时必须说明

要讲清楚为什么模糊匹配只提名不合并:错误合并两个议会,会在下游每个答案里造成无声且永久的错误;不合并则错误可见。这是一个可以写成设计原则的取舍,不要只描述流程。

B1 · 「子图」其实不是遍历采样的 代码核实

这是你问的核心问题,答案和直觉不同,必须在论文里说准。实现在 src/procurement_graph/qa/benchmark/samplers.py。

系统没有做图遍历式的子图采样。它的做法是在扁平记录全域上采「约束组」:

def _moderate_groups(records, columns, config, *, min_rows=None):
    grouped = records.groupby(columns, dropna=False).size().rename("n").reset_index()
    lower = config.min_evidence_rows if min_rows is None else min_rows
    grouped = grouped[grouped["n"].between(lower, config.max_evidence_rows)]   # 基数带
    for column in columns:
        text = grouped[column].astype(str).str.strip()
        grouped = grouped[grouped[column].notna() & text.ne("")
                          & text.ne("nan") & text.ne("None")]                  # 剔除空键
    return grouped.sort_values(["n", *columns]).reset_index(drop=True)         # 确定性排序

四个步骤,每一步都有方法学含义:

  1. 按列组合分组 —— 例如 ["release_year","tender_category"] 或 ["release_year","tender_cpv_id"]。组键就是未来的约束集。
  2. 基数带过滤 —— 只保留 n 落在 [min, max] 内的组。这一步同时排除了「记录太少所以答案退化」和「记录太多所以不可控」两类题。
  3. 空键剔除 —— 任何一个分组列取值为空 / nan / None 的组直接丢弃。
  4. 确定性排序 —— 按 (n, *columns) 排序后再采样,保证可复现。

_combined_groups() 在多个列组合上分别跑上面的流程,给每组打上 group_columns 标签后拼接; _sample_frame(grouped, n, rng) 用固定种子采样;_constraints_from_group(row) 把组键翻译成约束。

suppliers = {r["supplier_name"] for r in query(backend,

C — 双验证

独立求值器到底怎么实现的

C1 · 设计意图,以及它的独立性边界 代码核实

scripts/qa_independent_eval.py 的文档字符串把动机写得很清楚,建议在论文里转述:

纯 pandas 跑原始 node/edge parquet 表 —— 刻意不与 kg_interface / executor 共用代码。 目的是双验证:基准 oracle 由生成器/执行器家族产出,所以在一个独立实现从原始表重算出同样答案之前,「正确」是循环论证的。

它还记录了触发这件事的真实事故:worklog 2026-07-04 的 notice-vs-contract 计数单位漂移,正是从这个缺口溜过去的。这个细节非常适合写进论文,因为它说明双验证不是形式主义。

必须主动交代的独立性边界

脚本有两种 org 匹配约定,独立程度不同:

  • --convention edge(默认)—— load_frames() 直接读 contract_nodes、org_nodes、 buyer_of、supplier_of 四张原始表并自行 merge。完全独立。
  • --convention flat —— load_frames_flat() 会 import ParquetKGQueryBackend 来构造扁平视图。 此时独立的只是算子实现,记录全域的构造是共享的。源码注释自己写明了:"op implementations remain this module's own"。

论文里要说明 99.88% 是在哪个约定下取得的。默认是 edge,但请回到运行记录确认头条数字用的是哪一个。

C3 · 18 个残余分歧的代码级解释 代码核实

这是全文最能体现严谨的一段。那 18 个分歧不是随机噪声,而是求值器两处已知的启发式所致,并且代码里预先声明了它们:

# 文件顶部的显式声明
UNDERSPECIFIED_FAMILIES = {"date_relation", "boolean_field_equality", "comparison",
                           "numeric_threshold", "supplier_set_compare"}
# 注释:这些家族的 gold_plan 没有序列化全部参数
#      (阈值和比较方向只存在于题面)—— 借助题面解析评估,并单独报告。
  • 15 个 top_k 参数推断 —— rank_top_k 分支硬编码了「按计数取前三个买方」。 当黄金计划的 k 或分组字段不同时,两边就会不一致。
  • 3 个 boolean 表面解析 —— numeric_threshold 用 re.search(r"(?:gbp|£)\s*([\d,.]+)\s*(million|billion|m|bn)?", question) 从题面抠阈值; 抠不到就返回 threshold_unparsed。

写论文时的正确表述

不要写成「18 个无法解释的分歧」。要写成:求值器对五个参数未完全序列化的家族采用题面解析,这部分被显式标注并单独报告; 残余 18 例全部落在这两类已知启发式内,逐一人工检视,无一影响已报告的比较。 这样写,弱点反而变成方法学上的强项。

D3 · 编译 代码核实

graph_planning.py :: compile_graph_plan() 的早期拒绝理由(可以直接列进论文的失败分类):

  • missing_graph_plan —— payload 里没有 graph_plan
  • missing_graph_variables —— 变量表为空
  • missing_graph_return —— 缺 operation 或 input
  • runtime_rejected —— 运行期拒绝

依赖推导是这里最有技术含量的一段,值得在论文里单独写一小段。derive_depends_on() 从变量命名约定推出依赖, 但规划器经常用同一后缀表达相反的含义(b1a1 既可能是「喂给 a1」也可能是「派生自 a1」)。 处理办法:当命名推导与显式 depends_on 冲突时,以显式声明为准,丢弃命名推出的反向边,避免编译出二元环。 另外「关系 from S to T」被当作真实的数据流边,否则关系式桥接会静默地不绑定而全量执行。

论文/草稿 论文称有「十二个规范化变换 + 三道闸门(全程序可接地 / DAG 合法 / 无未受约束的绑定源)」。 未核实 我没有逐一数出这 12 个变换和 3 道闸门的代码位置,引用前请自行核对。

D4 · 执行 代码核实

executor.py :: execute_query_spec() 的流程:

  1. 跑 preflight_checks();任一失败即返回,并按失败类型映射状态: 缺字段 → schema_error;需穷举未满足 → incomplete_evidence;其余 → constraint_conflict。
  2. 检查操作是否在支持集内。已核实的 _SUPPORTED 共 10 个: select_unique, count, sum, exists, argmax, argmin, distinct_set, set, top_k, predicate; 不在集合内 → unsupported_operation。
  3. 快路径:count / exists 只需计数,走 backend.count() 加一个封顶采样 (_EVIDENCE_ID_CAP)取证据,使得 bridge 第二跳的巨大匹配集永远不会被完整物化。这是个真实的工程决策,值得写。

口径冲突预警

执行器的 _SUPPORTED 是 10 个操作,models.py 的 RuntimeAnswerOperation 是 12 个,而论文声称的算子代数是 17 个节点类型 + 7 种值类型。 这三者属于不同层:17 个是第 9 章递归代数的节点类型,12/10 个是 v1 运行期规格的答案操作。 论文里必须讲清是哪一层,否则会被认为数字对不上。

F — 收尾

动笔前必须自己确认的六件事

  1. 规模口径统一。 166,277 releases 与 215,221 award records 是两个不同的东西, 毕设摘要目前把后者写成了「releases」的角色。全文选一个主口径。
  2. 算子数量分层说明。 17(第 9 章递归代数节点)/ 12(RuntimeAnswerOperation)/ 10(执行器 _SUPPORTED) 分属不同层,必须讲清楚,否则看起来自相矛盾。
  3. 双验证的约定。 99.88% 是 edge 还是 flat 约定下取得的?回到运行记录确认,并在论文里写明独立性边界。
  4. 12 个变换 / 3 道闸门。 未核实 论文已经这样写了,但我没能在代码里逐一对上。引用前请自行数一遍。
  5. 入库四门控的实现位置。 未核实 建议在 qa/benchmark/gates.py 与 gate_b.py 里定位后再写。
  6. 训练文件行数与论文数字的个位数差异。 5,598/5,605、6,550/6,556 —— 找出原因或统一。

Methodology 的建议骨架(对标 ACL/EMNLP)

  1. Problem Definition —— 形式化:给定问题 q 与数据 D,学一个映射,使得答案由执行产生而非生成产生。你现在完全缺这一节。
  2. Framework Overview —— Interpreter / Planner / 确定性栈的分解,以及「模型提出、执行裁决」的边界。
  3. Program Language —— 值类型与算子清单、类型检查、文法编译成 JSON schema。
  4. Program Generation —— Reader 的 briefing 契约、Planner 的模板与受约束解码。
  5. Grounding & Execution —— 接地纪律、编译闸门、执行器快路径。
  6. Verification & Repair —— 五项检查、三轮修复上限、拒绝规则。
  7. Training Data Construction —— 候选采样、验收规则、自采集。这一节现在散在 Evaluation 里,要搬进 Method。
